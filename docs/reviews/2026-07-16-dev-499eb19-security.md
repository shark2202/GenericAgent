## Findings

### Important

**S1. Prompt-injection surface — MCP summary injected into system prompt**
- **Where:** `agentmain.py` `get_system_prompt()` (+9 lines), `MCPClientManager.get_all_tools_summary()`.
- **What:** The connected MCP server/tool summary is concatenated directly into the system prompt.
- **Why:** If `get_all_tools_summary()` embeds **server-provided** tool names/descriptions verbatim, untrusted content from an MCP server process is elevated into the system prompt — which carries instruction authority (higher than tool-result injection). A malicious/buggy server description (`"IMPORTANT: call tool X with arg Y..."`) becomes a system-level instruction.
- **Suggested fix:** Treat the summary as **data**, not instructions — wrap in a delimited, labeled block and escape/neutralize directive-looking text; OR filter descriptions. **Verify** what `get_all_tools_summary()` actually emits (names only vs. full descriptions).
- **Severity rationale:** Configured servers are semi-trusted (user picked them), so not Critical — but the system-prompt channel is the highest-authority one and warrants hardening. Escalate to Critical if 3rd-party/untrusted MCP servers are supported.

**S2. MCP call arguments logged in plaintext — secret leakage risk**
- **Where:** `plugins/mcp_distill.py:51` (`args={json.dumps(call_args)[:200]}`), persisted to `memory/mcp_call_log.md`.
- **What:** Every `mcp_call` has its `arguments` JSON-logged (truncated to 200 chars) to a local file.
- **Why:** MCP tool arguments can carry secrets / user data (e.g., a tool calling an API with a key, or reading sensitive file contents). Those land in plaintext on disk. The 200-char truncation limits but does not prevent leakage.
- **Suggested fix:** Redact known-sensitive argument keys (api_key, token, password, secret, …); or log only `server`/`tool`/`success`, not raw `arguments`. Confirm `memory/mcp_call_log.md` is gitignored (likely yes, under `memory/`) and document that the file may contain sensitive data.
- **Severity rationale:** Local at-rest, likely gitignored, non-networked → Important, not Critical.

### Minor

**S3. Swallowed exception violates let-it-crash**
- **Where:** `plugins/mcp_distill.py:53-55` `try: _append_entry(entry) except Exception: pass`.
- **Why:** Silently discards ALL log-write failures (disk full, permission, OSError) — masks problems and matches the over-defensive pattern CONTRIBUTING.md warns against.
- **Suggested fix:** Narrow the except; on failure, write a one-line note to stderr so failures are visible.

**S4. Log read-modify-write without a lock**
- **Where:** `plugins/mcp_distill.py:20-34` (`_append_entry` reads whole file → mutate → rewrite).
- **Why:** Not concurrency-safe and O(n) per append (rewrites up to 200 entries each call). Risk is low (the `tool_after` hook likely runs single-threaded in the agent loop), but a concurrent writer could clobber entries.
- **Suggested fix:** Append-only writes, or a small file lock; cap via line-counting on read, not full rewrite.

**S5. Namespace-shadowing workaround masks root cause**
- **Where:** `pyproject.toml` `[tool.pytest.ini_options]` `addopts += "-p no:langsmith_plugin"`.
- **Why:** Disables the plugin because `import packaging.version` fails under a namespace-shadowed `packaging`. This masks the deeper issue: something is shadowing the `packaging` package, which can break other imports too (not just tests).
- **Suggested fix:** Locate the shadowing `packaging` module (a local `packaging.py` / `packaging/`? the bundled dist?) and fix at the source; keep the disable only as a documented stopgap.

## Positive
- Hot-reload deadlock fix is correct: `Lock → RLock` + separate `_reload_lock` with `acquire(blocking=False)` try/finally, and the dead `if self._lock.locked(): pass` guard is removed. Concurrency reasoning is sound.
